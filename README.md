# MATCHIQ

MATCHIQ is an AI-powered B2B software selection and decision intelligence
platform. A business user describes a software requirement in plain English;
MATCHIQ extracts a structured requirement, asks a handful of clarification
questions, lets the team weight decision criteria, scores real vendor data
against those criteria with a **deterministic** engine, and produces an
explainable, printable decision report.

This is a portfolio demonstration build. The vendor catalogue is synthetic
demo data — no real vendor partnerships, pricing agreements, or
certifications are implied anywhere in the product.

## Quick start (demo mode — no configuration required)

```bash
npm install
npm run dev
```

Open http://localhost:3000. Click **Continue with demo account** on the
login screen (or sign up fresh — signup always works, no email verification
in this build). The demo account (`amelia@northfieldco.example`) comes
pre-loaded with five realistic decision scenarios across CRM, Project
Management, Accounting, HR, and Customer Support, in various stages from
draft through decided.

MATCHIQ works completely offline in this mode: no database, no API key, no
external service. See **Demo mode** below for exactly what that means.

## Local setup

```bash
git clone <this repo>
cd matchiq
npm install
cp .env.example .env.local   # optional — see below
npm run dev                  # http://localhost:3000
npm run test                 # run the test suite
npm run build && npm start   # production build
```

`.env.local` is entirely optional. Every environment variable in
`.env.example` has a working fallback:

| Variable | If unset |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Auth and data run on the in-memory demo store instead of Supabase |
| `SUPABASE_SERVICE_ROLE_KEY` | Only needed once Supabase is wired up |
| `OPENAI_API_KEY` | Requirement extraction and recommendation explanations use MATCHIQ's deterministic fallback engine instead of a live LLM call |

## Demo mode, precisely

"Demo mode" is not a stripped-down preview — it's the same application, same
services, same scoring engine, running against:

1. **An in-memory data store** (`src/lib/store/db.ts`) instead of Postgres.
   It's seeded on server start from `src/lib/demo-data/scenarios.ts` and
   mirrors the production schema in `/supabase/schema.sql` field for field.
   Restarting the dev server resets all data back to the seeded scenarios.
2. **A synthetic vendor catalogue** (68 vendors across 10 categories,
   `src/lib/demo-data/vendors.ts`, deterministically generated by
   `scripts/gen-vendors.mjs`). Every vendor page and card is labelled as demo
   data in the UI.
3. **A deterministic fallback in `AIService`** for requirement extraction and
   recommendation narration, used automatically whenever `OPENAI_API_KEY` is
   absent (see `ARCHITECTURE.md` for exactly what it does).
4. **Cookie-based demo authentication** (`src/lib/auth.ts`) instead of
   Supabase Auth. Signup creates a real new organisation + owner profile in
   the store; login looks up a profile by email. There are no passwords in
   this build — see `supabase/README.md` for the real auth path.

## Deploying to Vercel

MATCHIQ is a zero-config Next.js app — `vercel.json` only sets a memory/
timeout override for the PDF-generation route, nothing else is required.

### Option A — deploy as-is (demo mode, no database)

```bash
git push <your-repo> main       # this repo is already git-initialised
```

Then in Vercel: **New Project → import the repo → Deploy**. No environment
variables are required. You'll get a working, publicly-reachable MATCHIQ
instance with the same demo account and five seeded decision scenarios as
local dev.

**Read this before you rely on it for a live client demo:** Vercel runs each
route as an independent serverless function, and MATCHIQ's demo-mode store
is in-memory — there is no shared database behind it in this configuration.
Two things follow directly from that:

- **The seeded baseline (the demo account, its five decisions, the vendor
  catalogue) is fully reliable.** Every seed id is generated deterministically
  (`src/lib/demo-data/scenarios.ts`), so it's byte-identical no matter which
  function instance or cold start serves the request — verified by
  restarting the server between requests and diffing the ids. Logging in as
  the demo account and walking through those five decisions will behave the
  same on Vercel as it does locally, every time.
- **Anything you create live during a session — a new decision, a new
  signup, a comment, a criteria edit — is only held in the memory of
  whichever function instance handled that write.** A follow-up request that
  lands on a different (or newly cold-started) instance won't see it. Auth
  itself won't silently break in that situation (the session cookie carries
  your name/org directly, not just an id to look up — see `src/lib/auth.ts`),
  but your data might appear to have vanished. For a low-traffic personal
  demo this is often invisible in practice, but it is not something to rely
  on for anything real.

If that caveat matters for how you intend to use the deployed link, use
Option B.

### Option B — deploy with real persistence (recommended for anything client-facing beyond a live walkthrough)

1. Create a Supabase project and run `supabase/schema.sql` then
   `supabase/rls.sql` against it (`supabase/README.md` has the full
   walkthrough, including exactly which files change to move auth and every
   service off the in-memory store).
2. Set the environment variables from `.env.example` in the Vercel project
   settings (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY`).
3. Deploy as in Option A.

Either way, `next build` is already verified clean and has no dependency on
any bundled binary — the PDF export uses `pdfkit`, a pure Node library, so
it works unmodified on Vercel's serverless functions.

## Scoring engine

`src/lib/services/ScoringService.ts` computes eight sub-scores per vendor —
price, feature, integration, usability, security, support, implementation,
and value — purely from structured requirement + vendor data, using fixed
arithmetic. **No AI model is ever in the scoring path.** Given the same
requirement, criteria, and vendor record, the score is byte-identical every
time — this is asserted directly in `tests/scoring-service.test.ts`. Each
decision criterion (e.g. "Price", "Automation", a custom criterion someone
typed in) maps onto one of those eight dimensions by keyword, blended with a
small amount of direct keyword evidence from the vendor's own feature list,
so a criterion like "Slack integration" scores differently for a vendor that
actually lists Slack as an integration versus one that doesn't. See
`ARCHITECTURE.md` for the full algorithm.

## AI architecture

`src/lib/services/AIService.ts` is the single gateway to any language model
call, and it is scoped narrowly on purpose:

- **Requirement extraction** — turns free text into the structured
  `DecisionRequirement` shape. Tries an OpenAI-compatible `/chat/completions`
  call if `OPENAI_API_KEY` is set; otherwise (or on any failure) falls back
  to a deterministic keyword/regex extractor.
- **Clarification questions** — template-based; not an LLM call at all,
  because a fixed decision tree already covers what's worth asking.
- **Recommendation narration** — writes 1-2 plain-English sentences over
  numbers `ScoringService` already computed. The model (or the fallback
  template) is given only the vendor's own structured facts and the score
  breakdown; it is explicitly instructed never to introduce a price,
  feature, integration, or certification that isn't already in that data.

## Organisation-level security

Every decision, requirement, criterion, comment, vote, note, and report
belongs to an organisation. In demo mode this is enforced in each page/route
handler (`if (decision.organisationId !== session.organisationId)
notFound()`); in the Supabase-backed design (`supabase/rls.sql`), the same
boundary is enforced at the database level with Row Level Security, so even
a bug in application code cannot leak one organisation's decisions to
another. The vendor catalogue itself is the one deliberately public table —
anyone can browse it without an account.

## Report generation

Reports are generated server-side (`ReportService.generate`) as a frozen
JSON snapshot (so a report reflects the state at the moment it was
generated, not a live query), rendered two ways:

- An in-app printable page (`/decisions/[id]/report`) styled for
  `window.print()` / "Save as PDF".
- A genuine server-rendered PDF (`/api/decisions/[id]/report/pdf`) built with
  `pdfkit` — a pure Node.js PDF library with no headless-browser dependency,
  so it behaves identically in any deployment target including serverless.

## Connecting real vendor data later

`src/lib/adapters/VendorDataAdapter.ts` is the seam every vendor-sourcing
strategy implements. `VendorService` depends only on that interface. Three
implementations ship:

- `StaticDemoAdapter` — the synthetic catalogue (default, active today).
- `ExternalApiAdapter` — a stub calling a licensed vendor-data API.
- `CsvVendorAdapter` — a stub importing a client's own vendor research from
  CSV.

Swapping `VendorService`'s adapter to a real source is a one-line change;
`ScoringService`, `ComparisonService`, and every page/component are
unaffected because they only ever see the shared `Vendor` type.

## Scaling notes

- The scoring engine is pure and stateless — it can run in a serverless
  function, a queue worker, or client-side with no changes.
- Analytics events and AI usage records are append-only and organisation-
  scoped, so they partition cleanly if MATCHIQ outgrows a single Postgres
  instance.
- `VendorDataAdapter` means the vendor catalogue can move from a
  few-hundred-row demo table to a syndicated feed of tens of thousands of
  vendors without touching scoring, comparison, or UI code — only the
  adapter and its caching strategy change.
- Report snapshots are immutable JSON blobs, so report history storage
  scales independently of the live decision data.

## Testing

```bash
npm run test
```

29 tests cover: deterministic scoring and reproducibility, budget matching,
feature matching, ranking stability, criteria weight normalisation,
requirement extraction (category/budget/feature detection), clarification
answers folding back into the requirement, decision status lifecycle,
organisation access isolation, shortlist management, voting, comments/
mentions, and analytics event tracking.

```
    demo-data/          Synthetic vendor catalogue + seeded demo scenarios

    auth.ts             Demo cookie auth (Supabase-Auth-ready)
  app/
    (marketing)         Public landing page
    (app)/              Authenticated app shell: dashboard, decisions,

    vendors/            Public vendor directory + detail pages

  schema.sql            Full production Postgres schema
  rls.sql               Row Level Security policies
  README.md             How to go from demo mode to a real deployment
scripts/
  gen-vendors.mjs        Regenerates the synthetic vendor catalogue
tests/                   Vitest suite
```
